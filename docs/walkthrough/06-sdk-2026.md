# Walkthrough 06b: the SDK client in the 2026-07-28 era

The SDK client (`clients/sdk/`) can speak the 2026-07-28 revision too:
`node clients/sdk/src/main.ts tour --era 2026-07-28 -- <server command>`, or
`scripts/record.sh --client sdk-tour-2026`. It runs the raw client's 2026 tour
([walkthrough 06](06-era-2026.md)) step for step with the same inputs, through
`@modelcontextprotocol/client` 2.3.1. This walkthrough reads the two clients' traces side by side:
what `tap.diff` reports, entry by entry, and the two things it hides on purpose (string ids, and
a second process that the lab's transport avoids). Record your own and diff them:

```console
scripts/record.sh --client tour-2026 mine-raw
scripts/record.sh --client sdk-tour-2026 mine-sdk
python3 -m tap.check runs/<your-sdk-run>/trace.jsonl --revision 2026-07-28
python3 -m tap.diff runs/<your-raw-run>/trace.jsonl runs/<your-sdk-run>/trace.jsonl --explain docs/walkthrough/06-sdk-2026.md#sdk-diff
```

`tap.diff` names each message by direction, method and occurrence, never by id (the same keys as
walkthrough 05). Citations: `sdk:` points into the installed SDK package
(`clients/sdk/node_modules/@modelcontextprotocol/`); `servers:` is the pinned everything server.

## What is the same

The two traces hold the same 74 messages in the same order: nothing is in one trace only. Of the
74 pairs, 30 are equal and 44 differ, and the differences are all of the kinds below. In the
2025 era the raw client had to make its own message ids match the SDK's to be compared by id;
here the keys make that unnecessary, and the numbers do not agree. Both clients number requests
from 0 in send order, but the SDK's probe and listen request use string ids outside that count,
so the long-running call that is cancelled is id 14 in the raw trace and 13 in the SDK trace.

## What `tap.diff` normalises away, and `tap.show` shows

`tap.diff` ignores ids, so two things are visible only in `tap.show`:

- **The probe's id.** The SDK's `server/discover` is sent as the string
  `"server-discover-probe-1"`, not a number
  (`sdk:client/dist/index.mjs:2671` "const id = `server-discover-probe-${++this._probeCounter}`;"),
  so that it can never collide with the SDK's numeric ids. The raw client's discover is id 0.
- **The subscription's id.** The SDK names its `subscriptions/listen` request `"listen:0"`
  (`sdk:client/dist/index.mjs:3987` "const listenId = `listen:${this._nextListenId++}`;"), a string
  too; the raw client uses the next number of its own counter. Every notification on the stream is
  tagged with it in `_meta`, which is why the five stream notifications appear in the diff.

## The sibling probe the lab's transport avoids

With the SDK's own `StdioClientTransport` and a pinned era, `connect` does not send
`server/discover` on the connection it will use. It spawns a second, short-lived process from the
same command, asks it, and throws it away
(`sdk:client/dist/index.mjs:2898` "async function negotiateStdioViaSibling(negotiation, sessionTransport, params, deps) {"),
because some stdio servers exit on any request that comes before `initialize`. The choice is made
by `readStdioServerParams`, which hands over the spawn parameters only to the base class itself
(`sdk:client/dist/index.mjs:2880` "function readStdioServerParams(transport) {"; the caller at
`sdk:client/dist/index.mjs:3404` "}) : await negotiateStdioViaSibling(negotiation, transport, stdioParams, baseDeps);").

Under `scripts/record.sh` the "second process" is a second tap writing to the same trace path, and
the tap truncates the file when it opens it (`tap/__main__.py`): the trace of the real session
would be missing its `server/discover`. The lab's SDK client therefore uses a subclass of the
transport with no members (`InPlaceStdioTransport` in `clients/sdk/src/era.ts`). A subclass is
not "exactly the base class", so the SDK probes in place: one process, and the trace starts with
`server/discover`. Measured on 2026-10-22: the base class started two processes and the first trace
held only `server/discover` and its result; the subclass started one. The 2025 modes never probe
and use the base class.

What the SDK cannot do in this era is the tasks extension: it rejects a `resultType` it does not
handle (`sdk:client/dist/src-WCy6ifGf.mjs:3993` "Unsupported result type '${rawResultType}' for ${method}"),
so the SDK client has no tasks run.

## sdk-diff

What `tap.diff` reports between a fresh `tour-2026` and a fresh `sdk-tour-2026` trace, entry by
entry. Nothing is in one trace only. Most entries share one difference: the clients name
themselves. The envelope's `clientInfo` is `wire-lab-raw` 0.2.0 in the raw client and
`wire-lab-sdk` 0.5.0 in the SDK client (`clients/sdk/src/client.ts`, `CLIENT_INFO`); every other
member of every envelope is equal, because the SDK builds the same three reserved keys
(`sdk:client/dist/src-WCy6ifGf.mjs:3925` "[PROTOCOL_VERSION_META_KEY]: material.protocolVersion,").
`clientInfo` is the one key of the three that is not required, but clients SHOULD send it on
every request
(`spec:docs/specification/2026-07-28/basic/index.mdx:384` "Clients **SHOULD** include `io.modelcontextprotocol/clientInfo` on every request"),
which is why it differs in every request and not only in the first. Each note below says what
else the frame teaches.

#### `c2s.server/discover#0`
The probe. The raw client sends `server/discover` as id 0 and the SDK as
`"server-discover-probe-1"`, which the diff does not show (see above). Its envelope is the
same apart from `clientInfo`, and that envelope is what pins this stdio connection to 2026-07-28
(walkthrough 06, `## source-tour`, step 2). The server's reply is not an entry: both clients get
the same `DiscoverResult`, because nothing in it depends on who asked.

#### `c2s.tools/list#0`
The first request with a numeric id, and the place where the two clients' ids part. The SDK's
probe used a string id, so its numeric counter
(`sdk:client/dist/src-WCy6ifGf.mjs:6170` "const messageId = this._requestMessageId++;") starts
here at 0; the raw client's discover took 0, so its `tools/list` is 1. From here every SDK id is
one less than the raw client's (two less after the listen request, below). The diff pairs by
method and occurrence, so the shift is invisible in it. The SDK also writes the members in another
order (`method` and `params` first, then `jsonrpc` and `id`,
`sdk:client/dist/src-WCy6ifGf.mjs:6173` "...request,"); JSON members have no order, and the diff
compares values, not bytes.

#### `c2s.tools/call#0-3`
`echo`, `get-sum` and the two log-level calls. Only `clientInfo` differs: the tool name and
`arguments` are equal, and so is the log level (absent, then `warning`), because both put it in
`_meta`, where 2026-07-28 moved it from `logging/setLevel`. The five log messages that the second
call produces are equal in both traces and are not entries.

#### `c2s.resources/list#0`
Only `clientInfo` differs, and the reply is not an entry: the server returns the same seven
resources to both clients. The list's `cacheScope` is `"public"`, the server's statement that the
answer holds no caller-specific data
(`spec:docs/specification/2026-07-28/server/utilities/caching.mdx:173` "A `cacheScope` of `\"public\"` indicates that the response does not contain user-specific data"),
and the two equal replies are consistent with that.

#### `c2s.resources/templates/list#0`
Only `clientInfo` differs. Neither client sends a `cursor`, and the reply has no `nextCursor`, so
the three templates come in one page
(`spec:docs/specification/2026-07-28/server/utilities/pagination.mdx:99` "Treat a missing `nextCursor` as the end of results").
The same holds for every list in the tour.

#### `c2s.resources/read#0`
Only `clientInfo` differs: both read the same `uri`, the static architecture document, and get the
same text with `ttlMs` 3600000 (one hour), against 60000 (one minute) on the lists. A cache hint
belongs to each result, not to the connection.

#### `c2s.prompts/list#0`
Only `clientInfo` differs. Every result in this era also names the server, in
`_meta["io.modelcontextprotocol/serverInfo"]`
(`spec:docs/specification/2026-07-28/basic/index.mdx:397` "every result's `_meta`, unless specifically configured not to do so, to"):
the mirror of `clientInfo`, and equal in both traces because it is the same server.

#### `c2s.prompts/get#0-1`
`simple-prompt`, then `args-prompt` with `city` set to `Oslo`. Only `clientInfo` differs. The first
request has no `arguments` member in either trace: the SDK's `getPrompt({ name })` leaves it out
as the raw client does, so the two requests are equal apart from the envelope.

#### `c2s.completion/complete#0`
Only `clientInfo` differs: the same `ref` (`{"type": "ref/prompt", "name": "completable-prompt"}`)
and `argument` (`department`, prefix `E`), and the same answer, `Engineering`.

#### `c2s.tools/call#4`
The long-running call that completes. The raw client chose the progress token `"tour-done"`; the SDK
asked for progress with `onprogress` and chose the token itself, the request's own id
(`sdk:client/dist/src-WCy6ifGf.mjs:6183` "progressToken: messageId"), here 12. The spec lets the client pick a token any way it likes, as long as it is unique among its
active requests
(`spec:docs/specification/2026-07-28/basic/patterns/progress.mdx:17` "Progress tokens can be chosen by the client using any means"),
so both are valid. The client's name and version
differ as in every request.

#### `s2c.notifications/progress#0-1`
The two progress notifications of that call. The server copies the token it was given, so they
differ for the same reason as the request.

#### `c2s.tools/call#5`
The long-running call that is cancelled: the token is `"tour-cancel"` in the raw trace and the
request's id (13) in the SDK trace, and the client's name and version differ.

#### `s2c.notifications/progress#2-3`
The two progress notifications of the cancelled call, `"tour-cancel"` against 13. The server
ignores the cancellation and sends both (a departure from the spec that walkthrough 06 records);
the SDK, which has forgotten the token, reports the second one on stderr and drops it.

#### `c2s.notifications/cancelled#0`
The SDK puts the envelope on a notification too: `params._meta` holds the three reserved keys in
the SDK trace and is absent in the raw trace, which follows the schema (a notification is not a
request, and has no `RequestMetaObject`). The SDK attaches the envelope to everything it sends once the era is
pinned. The server accepts it. The `requestId` names the cancelled call: 14 in the raw trace and
13 in the SDK trace. The diff maps a `requestId` to the key of the request it names, the same
`tools/call` in both, so that difference is not reported.

#### `c2s.subscriptions/listen#0`
Opens the notification stream. Only `clientInfo` differs in the diff; the `notifications` filter is
equal. The id is where the clients really differ: `"listen:0"` from a counter of the SDK's own
(`sdk:client/dist/index.mjs:3096` "and Protocol's numeric `_requestMessageId` counter only ever issues"),
so it can never collide with an ordinary request's id, against the next number, 15, in the raw
trace. Either is a valid JSON-RPC id. Because the listen request does not use the SDK's numeric
counter, the next `tools/call` is 14 in the SDK trace and 16 in the raw one.

#### `s2c.notifications/subscriptions/acknowledged#0`
The `subscriptionId` in `_meta`: the id of the client's listen request, a number in the raw trace
and `"listen:0"` in the SDK trace.

#### `c2s.tools/call#6`
The first `trigger-list-changed` call (`tools`). The request differs only in `clientInfo`; the
notification it causes is tagged with the listen request's id, not with this call's, which is why
the next entry differs in `subscriptionId` and this one does not. The call's own result is equal.

#### `s2c.notifications/tools/list_changed#0`
The notification's `subscriptionId`, as in the acknowledgement.

#### `c2s.tools/call#7`
The second `trigger-list-changed` call (`prompts`). As for the first: only `clientInfo` differs,
and the change it announces goes to the stream, not to this request.

#### `s2c.notifications/prompts/list_changed#0`
The notification's `subscriptionId`, as in the acknowledgement.

#### `c2s.tools/call#8`
The third `trigger-list-changed` call (`resources`). Only `clientInfo` differs. The server sends
a list change only to a stream whose filter asked for it; both filters set
`resourcesListChanged`, so both traces have the next entry.

#### `s2c.notifications/resources/list_changed#0`
The notification's `subscriptionId`, as in the acknowledgement.

#### `c2s.tools/call#9`
The `trigger-resource-update` call for the static document. Only `clientInfo` differs. The update
reaches the client because both listen filters named that URI in `resourceSubscriptions`
(`spec:docs/specification/2026-07-28/basic/patterns/subscriptions.mdx:47` "Receive `notifications/resources/updated` for these resource URIs").

#### `s2c.notifications/resources/updated#0`
The notification's `subscriptionId`, as in the acknowledgement.

#### `c2s.tools/call#10-13`
The call without capabilities (answered `-32021`), the two rounds of `get-roots-list`, and the first
round of `trigger-sampling-request`. Only the client's name and version differ. The SDK sends an empty
`clientCapabilities` for the first one because the tour overrides that reserved key per call, as the raw client does
(`sdk:client/dist/src-WCy6ifGf.mjs:3925` "[PROTOCOL_VERSION_META_KEY]: material.protocolVersion,"
builds the envelope, and a caller's own `_meta` keys win).

#### `c2s.tools/call#14`
The second round of `trigger-sampling-request`: the retry carries `inputResponses`, and the sampling
answer's canned text names the client: `canned reply from wire-lab-raw` against
`canned reply from wire-lab-sdk` (`clients/sdk/src/handlers.ts`, `CANNED_TEXT`). The SDK built the
retry itself, from the handler's return value, in the same shape as the raw client's
(`inputResponses` keyed as the server's `inputRequests`).

#### `s2c.response:tools/call#14`
The server's final result of the sampling call. It quotes the client's canned text
(`servers:src/everything/tools/trigger-sampling-request.ts:94` "LLM sampling result"), so it differs
wherever that text does.

#### `c2s.tools/call#15-16`
The two rounds of `trigger-elicitation-request`. Only the client's name and version differ: both
clients accept the form from its defaults.

#### `c2s.tools/call#17`
The first round of `trigger-multi-step-elicitation`. Only `clientInfo` differs: a first round is
an ordinary request, with no `inputResponses` and no `requestState`. The server's reply, the next
entry, is where the two traces start to differ.

#### `s2c.response:tools/call#17`
The first `input_required` result. Its `requestState` is a signed string that carries an expiry
time (it decodes to `{"p":{"step":"awaiting-name"},"exp":<seconds>}` before the signature), so it
is different on every run: this is noise, and a raw-vs-raw diff of two fresh traces shows it too.

#### `c2s.tools/call#18`
The second round. It carries the previous round's `requestState` byte for byte (so it differs
where that does) and the client's name and version.

#### `s2c.response:tools/call#18`
The second `input_required` result, with its own `requestState`: noise, as above.

#### `c2s.tools/call#19`
The third round, carrying the second round's `requestState`, and the client's name and version.

#### `c2s.notifications/cancelled#1`
The close of the subscription. Two differences. The SDK's `close()` sends no reason; the raw client sends
`"the client closes the subscription"`. And, as for the first cancellation, the SDK's carries the envelope.
The `requestId` is the listen request's id (a string, `"listen:0"`, in the SDK trace).
