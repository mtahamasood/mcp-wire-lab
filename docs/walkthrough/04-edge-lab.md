# Walkthrough 04: the edge lab, experiment by experiment

Eight experiments, each breaking exactly one rule after a normal 2025-era handshake (except the
one where the handshake is the rule). Record your own trace of one, then read it with its notes.
Notes are grouped under a `##` heading per experiment, and `--explain` takes the experiment's name
after a `#`:

```console
scripts/record.sh tests/fixtures/edge-unknown-method.ndjson
python3 -m tap.show runs/<your-run>/trace.jsonl --explain docs/walkthrough/04-edge-lab.md#unknown-method
```

| Experiment (`#name`) | Fixture |
| --- | --- |
| `missing-jsonrpc` | `tests/fixtures/edge-missing-jsonrpc.ndjson` |
| `before-initialize` | `tests/fixtures/exp-list-first.ndjson` (phase 1's, reused) |
| `unknown-method` | `tests/fixtures/edge-unknown-method.ndjson` |
| `duplicate-id` | `tests/fixtures/edge-duplicate-id.ndjson` |
| `string-id` | `tests/fixtures/edge-string-id.ndjson` |
| `notification-with-id` | `tests/fixtures/edge-notification-with-id.ndjson` |
| `batch-array` | `tests/fixtures/edge-batch-array.ndjson` |
| `oversized-frame` | generated by `tests/test_e2e.py` (a 1 MiB `tools/call`), never committed |

The note format, the anchors and the citation rules are those of
[walkthrough 01](01-handshake-2025.md). The notes under `## shared` explain the frames every
experiment has in common; an experiment's own notes win over them, and a shared note an experiment
does not use is not an error. Citations point into the pinned submodules: `spec` is the 2025-11-25
revision of the specification (plus, for batching, the 2025-06-18 changelog), `servers` is the
everything server. Where the server's behaviour comes from the TypeScript SDK (request routing,
message validation, error replies) there is no line to cite: the SDK is fixed by the server's
lockfile but is not a submodule, so those notes cite the spec and say so.

Reading the verdicts. Each experiment ends with one line: *follows the spec*, *stricter* (the
server refuses something the spec allows), *looser* (the server accepts something the spec
forbids or discourages) or *spec silent* (the spec has no rule to compare against).

Two things the driver does for these fixtures (phase 4 D2). A line carrying
`"_drive":{"expect":"none","wait_ms":N}` is sent without that member, and the driver then waits
`N` ms instead of waiting for a reply with the same id, because the server may never send one. And
`scripts/record.sh` reports a non-zero server exit (the everything server exits 1 after a transport
error) instead of failing: the exit code is the last record of the trace.

## shared

#### `tap.spawn.0`

The tap starts the server as a child process, exactly as in walkthrough 01. Nothing about the
experiment shows here; the `spawn` record lists the command and the minimal environment.

#### `c2s.initialize.0`

The client's `initialize` request, byte for byte as the fixture wrote it (walkthrough 01 explains
its fields). Its place in the experiment differs: in `before-initialize` something else goes first.

#### `stderr.0`

The server's boot line, `Starting default (STDIO) server...`, printed by
`servers:src/everything/transports/stdio.ts:92` "Starting default (STDIO) server...". Stderr is the
server's log channel, not protocol (see walkthrough 01).

#### `s2c.response.0`

The server's answer to `initialize`: the same reply as in walkthrough 01, matched to the request by
`id` 0. It carries the protocol version the server chose (`2025-11-25`) and its capabilities.

#### `c2s.notifications/initialized.0`

The client's `initialized` notification, which completes the handshake: a notification has no `id`
and so gets no reply (`spec:docs/specification/2025-11-25/basic/index.mdx:96` "MUST NOT** send a response").

## missing-jsonrpc

A request that has `id` and `method` but not `"jsonrpc":"2.0"`, followed by a `ping` to see whether
the connection survived. Predict first: does the server answer `tools/list` with a result, with an
error, or with nothing?

#### `c2s.tools/list.1`

The broken message: `{"id":1,"method":"tools/list"}`. The spec's request shape has the version
member (`spec:docs/specification/2025-11-25/basic/index.mdx:37` "jsonrpc: \"2.0\";") and the schema
fixes it (`spec:schema/2025-11-25/schema.ts:14` "JSONRPC_VERSION = \"2.0\""). The viewer still calls
it a request, because it has an `id` and a `method`. The driver sent it with `_drive`
`expect: none`, so it waited a second for a reply that never came.

#### `stderr.1-106`

There is no reply on stdout. The server's only reaction is on stderr: `Transport error: ZodError`
and then the validation failure, which says `jsonrpc` was expected to be `"2.0"` in every
alternative the message was tried against (request, notification, result, error), plus a stack that
starts in the SDK's message parsing. It is printed by the server's own error hook at
`servers:src/everything/transports/stdio.ts:65` "console.error(\"Transport error:\", error);".
The parsing and the validation are in the SDK (not cited). The message is dropped: the SDK never
hands it to a request handler, so there is no `id` to put on an error reply.

#### `c2s.ping.2`

The fixture's liveness check, sent after the broken request. The message is intact JSON-RPC.

#### `s2c.response.2`

The reply to the ping arrives at once (`"result":{}`): the bad message did not close the connection
or damage the session. The client never learns that `tools/list` was dropped except by the silence.

#### `tap.exit.0`

The driver closes stdin and the server exits with code 1, not 0. That is deliberate in the server:
its transport error hook sets the exit status, `servers:src/everything/transports/stdio.ts:66` "process.exitCode = 1;".
The spec forbids what the client did (`spec:docs/specification/2025-11-25/basic/transports.mdx:34` "write anything to the server's") but says
nothing about what a receiver does with it.

**Verdict: spec silent.** The message is invalid and the spec says the client must not send it; it names no
reply, and JSON-RPC's `-32600` (`spec:schema/2025-11-25/schema.ts:174` "INVALID_REQUEST = -32600") is
defined but this server does not use it here.

## before-initialize

Phase 1's `exp-list-first.ndjson`: `tools/list` is the first message, `initialize` comes after.
Predict first: does the server refuse a request before the handshake?

#### `c2s.tools/list.1`

A request before the server has said anything. The spec asks clients not to do this: they should
not send anything but pings until the server has answered `initialize`
(`spec:docs/specification/2025-11-25/basic/lifecycle.mdx:157` "SHOULD NOT** send requests other than").

#### `s2c.response.1`

The server answers `tools/list` with the full tool list and no error, about 280 ms in, the time the
server took to boot. This is the first reply of the run and it comes before the reply to
`initialize`: the server has no state that says "not initialised yet" for this request. Routing is
in the SDK (not cited); the tools come from the registration at
`servers:src/everything/tools/index.ts:47` "registerEchoTool(server)" and its neighbours.

#### `tap.exit.0`

The `initialize` and `initialized` messages follow and are answered normally (the shared notes), and
the server exits 0.

**Verdict: looser.** The spec says a client should not send this (a `SHOULD NOT`, so the client's
duty) and gives the server no duty to refuse; this server accepts it, which is more permissive than
the lifecycle section's intent.

## unknown-method

A request for a method nobody defined, after a normal handshake: `does/not/exist`. Predict first:
an error, which code, and does the server close the connection?

#### `c2s.does/not/exist.1`

A well-formed request (it has `jsonrpc`, an integer `id`, a `method`), so the receiver must answer
it. The method is in no spec.

#### `s2c.response.1`

An error response, not a result, with the same `id` 1 and code `-32601`, `Method not found`. The
spec's schema defines that code for exactly this case
(`spec:schema/2025-11-25/schema.ts:175` "METHOD_NOT_FOUND = -32601"), and an error reply has to carry the
request's id (`spec:docs/specification/2025-11-25/basic/index.mdx:89` "Error responses **MUST** include the same ID"). The SDK
produces it when no handler is registered for the method (not cited). `tap.show` lists it as an
`error id=1 code=-32601`.

#### `tap.exit.0`

The connection stays healthy, the session ends normally at stdin close, and the exit code is 0.

**Verdict: follows the spec.** Unknown methods get `-32601` with the request's id.

## duplicate-id

Two requests with the same `id` 1 in flight at once: a slow `tools/call` (a one-second
`trigger-long-running-operation`) and, 100 ms later, a quick `tools/list`. Predict first: does the
server refuse the second, and which reply does the client see first?

#### `c2s.tools/call.1`

The first request, id 1. The tool waits `duration / steps` per step
(`servers:src/everything/tools/trigger-long-running-operation.ts:53` "setTimeout(resolve, stepDuration * 1000)"), so the reply takes
about a second. The driver sent it with `expect: none` and waited 100 ms, so id 1 is still in
flight when the next line goes.

#### `c2s.tools/list.1`

The same id on a different request. The spec forbids reusing an id within a session
(`spec:docs/specification/2025-11-25/basic/index.mdx:48` "MUST NOT** have been previously used"). `tap.show` flags it
`(id already in flight)`.

#### `s2c.response.1`

Two frames have this anchor, and both are replies with `id` 1: first the tool list (to the second
request, in a few milliseconds), then, about a second after the first request, the long-running
tool's result (`Long running operation completed...`, text at
`servers:src/everything/tools/trigger-long-running-operation.ts:75` "Long running operation completed."). The server tracks in-flight
requests by id in the SDK (not cited) but did not refuse the clash. A client that matched replies by
id alone would hand the tool list to whichever request it considered first; only the content and
the order tell them apart. The viewer pairs the first reply with the later request for the same
reason.

#### `c2s.ping.2`

A third request with a fresh id; `expect: none` with a 1.5 s wait keeps the session open until the
slow reply has arrived.

#### `s2c.response.2`

The ping is answered at once, while the long operation is still running: the server handles
requests concurrently.

#### `tap.exit.0`

stdin closes after the long reply, the server exits 0.

**Verdict: looser.** The id reuse is the client's breach of a `MUST NOT`; the server neither rejects
it nor disambiguates, and answers both.

## string-id

The same request twice, `tools/list` with `"id": 1` and then with `"id": "1"`. Predict first: does
the server treat them as one id, and does the reply keep the type?

#### `c2s.tools/list.1`

The request with the integer id `1`.

#### `s2c.response.1`

The tool list, with `"id":1` in the reply: an integer, as sent.

#### `c2s.tools/list."1"`

The same request with the string id `"1"`. A request id may be a string or an integer
(`spec:docs/specification/2025-11-25/basic/index.mdx:46` "string or integer ID", and `spec:schema/2025-11-25/schema.ts:122` "RequestId = string | number").
The anchor keeps the quotes: the viewer treats `1` and `"1"` as different ids.

#### `s2c.response."1"`

The tool list again, and this time the reply carries `"id":"1"`, the string. The server keeps the id's
JSON type and does not collapse the two, so a client that stores its pending requests in a map
keyed by the id must key by value *and* type (the fixture driver compares them in Python, where
`1 == "1"` is false). Nothing is rejected, and the second request is not a reuse of the first id.

#### `tap.exit.0`

Both replies arrived, the server exits 0.

**Verdict: follows the spec.** Both id types are allowed and echoed unchanged; whether `1` and `"1"`
count as the same id is not stated, and the server treats them as different.

## notification-with-id

A message whose method is a notification (`notifications/cancelled`) but which carries an `id`:
`{"jsonrpc":"2.0","id":1,"method":"notifications/cancelled","params":{"requestId":99}}`. Predict
first: is it a notification (no reply) or a request (a reply)?

#### `c2s.notifications/cancelled.1`

What makes a message a notification is not its method name but the absence of an `id`
(`spec:docs/specification/2025-11-25/basic/index.mdx:108` "Notifications **MUST NOT** include an ID"). With an id it is a request, whose
method just happens to start with `notifications/`. The viewer shows it as a request
(`c2s.notifications/cancelled.1`, keyed by its id, not by occurrence). Sent as a notification, a
cancellation for an unknown request would simply be ignored
(`spec:docs/specification/2025-11-25/basic/utilities/cancellation.mdx:77` "Invalid cancellation notifications").

#### `s2c.response.1`

The server answers, with an error: `-32601 Method not found`, id 1. It routed by shape: an `id`
means request, and the server has no *request* handler for that method name. The notification
handler for `notifications/cancelled` was never consulted. (Routing is in the SDK, not cited.)

#### `c2s.ping.2`

A liveness check after the odd message, sent a second later.

#### `s2c.response.2`

Answered normally: the connection is intact.

#### `tap.exit.0`

Exit code 0.

**Verdict: follows the spec.** A message with an `id` is a request, so it gets a reply (`-32601`)
rather than being swallowed as a notification.

## batch-array

A JSON array of two requests on one line, then a plain `ping`. JSON-RPC 2.0 allows batches; MCP
removed them. Predict first: two replies, an error, or silence?

#### `c2s.batch.0`

One frame whose JSON is an array: `[{"jsonrpc":"2.0","id":1,"method":"tools/list"},{...,"id":2,"method":"ping"}]`.
MCP 2025-03-26 had batching; the 2025-06-18 revision removed it
(`spec:docs/specification/2025-06-18/changelog.mdx:12` "Remove support for JSON-RPC") and the 2025-11-25 transport says
messages are single ones (`spec:docs/specification/2025-11-25/basic/transports.mdx:27` "individual JSON-RPC requests"). The
fixture driver, which only sends lines, did not wait for any reply to it.

#### `c2s.ping.3`

A plain ping with id 3, sent right after; the driver waits a second for whatever comes back.

#### `stderr.1-50`

The server's parser rejects the array: `Transport error: ZodError` with, in each alternative,
`Invalid input: expected object, received array`. The same hook prints it
(`servers:src/everything/transports/stdio.ts:65` "console.error(\"Transport error:\", error);") and neither request in the array is
answered or even seen by a handler; the stack is the SDK's message parsing (not cited). The lines
may interleave with the next reply in the trace, which is why the range of stderr lines is one note.

#### `s2c.response.3`

The single ping is answered: the connection survives, and replies exist only for the unbatched
message. The two batched requests, ids 1 and 2, get nothing.

#### `tap.exit.0`

Exit code 1, from the transport-error hook (`servers:src/everything/transports/stdio.ts:66` "process.exitCode = 1;").

**Verdict: follows the spec.** The spec's messages are single requests, notifications and responses; a
batch is not a valid message, and the server refuses to process it (silently on the wire, loudly on stderr).

## oversized-frame

One `tools/call` of `echo` whose `message` argument is a string of 1 MiB (1,048,576 `x`), so the
frame is 1,048,675 bytes. The test that records it generates the fixture. Predict first: is there a
size limit?

#### `c2s.tools/call.1`

A single line of 1,048,675 bytes. The tap records it whole (its `bytes` field says so) and forwards it
unchanged. The spec says only that messages are delimited by newlines
(`spec:docs/specification/2025-11-25/basic/transports.mdx:28` "Messages are delimited by newlines") and gives no size.

#### `s2c.response.1`

The server echoes it all back in one frame of 1,048,656 bytes (`Echo: ` plus the message plus the
reply envelope; the tool builds it at `servers:src/everything/tools/echo.ts:36` "Echo: ${validatedArgs.message}"),
in about 30 ms. There is no limit at this size, in the tap, the driver or the server.

#### `tap.exit.0`

Exit code 0.

**Verdict: spec silent.** The spec sets no maximum message size, and the server and the tap
accept 1 MiB; a limit, if any, would be somewhere above it.
