# Walkthrough 06: the 2026-07-28 era, frame by frame

This explains the raw client speaking the 2026-07-28 revision of the protocol to the pinned
everything server over stdio, and how that differs from the 2025-11-25 era of walkthrough 02. It
has four sections of notes, read with `--explain <file>#<section>`:

- `## tour`: one note per frame of a fresh `tour-2026` trace;
- `## tasks`: one note per frame of a fresh `tasks-2026` trace;
- `## shared`: the notes both traces use (the opening, the exit);
- `## era-diff`: one note per entry `tap.diff` reports between a fresh 2025 `tour` trace and a
  fresh `tour-2026` trace.

```console
scripts/record.sh --client tour-2026
python3 -m tap.check runs/<your-run>/trace.jsonl --revision 2026-07-28
python3 -m tap.show runs/<your-run>/trace.jsonl --explain docs/walkthrough/06-era-2026.md#tour
scripts/record.sh --client tour
python3 -m tap.diff runs/<the-2025-run>/trace.jsonl runs/<the-2026-run>/trace.jsonl --explain docs/walkthrough/06-era-2026.md#era-diff
```

Anchors are as in walkthrough 02 (`<direction>.<method or response>.<id or occurrence>`; ids run
from 0 in send order) for `tap.show`, and `tap.diff`'s keys (`<dir>.<method>#<n>`,
`<dir>.response:<method>#<n>`, `n` counting that method in that direction from 0) in
`## era-diff`. Citations point into the pinned submodules: `spec` is the 2026-07-28 revision of
the specification (docs under `docs/specification/2026-07-28/`), `servers` is the everything
reference server. The server's protocol plumbing lives in the TypeScript SDK's server package
(`serveStdio`, request routing, building replies), which is not a submodule and cannot be cited
here; those notes cite the spec for the rule and the server for what it configures.

## Five shifts, and what each 2025 message became

1. **Discovery instead of a handshake.** `initialize` and `notifications/initialized` are gone.
   The client may ask `server/discover` (this client always does, first and alone) and learns the
   supported versions, the capabilities and the server's name from the reply. The era of a stdio
   connection is pinned by its first message: an envelope means 2026-07-28.
2. **An envelope on every request instead of a session.** Each request's `params._meta` carries
   the protocol version, the client's info and the client's capabilities, and optionally a log
   level. The server keeps nothing between requests, so it may not infer anything from earlier
   ones.
3. **Input requests carried in results instead of server-to-client requests.** The server never
   writes a request to the client. It answers with a result of type `input_required` and the
   client retries the same request with the answers.
4. **A subscription stream instead of `resources/subscribe` and unsolicited notifications.**
   `subscriptions/listen` opts in to list changes and resource updates; each notification on the
   stream is tagged with the id of the listen request.
5. **Tasks as an extension.** The core protocol no longer has them. A client declares
   `io.modelcontextprotocol/tasks` in its envelope and a server may then answer a `tools/call`
   with a task handle (`resultType: "task"`).

| 2025-11-25 (walkthrough 03, `server-tour`) | 2026-07-28 (`tour-2026`) |
| --- | --- |
| server sends `roots/list` to the client | `tools/call get-roots-list` answers `input_required` with `inputRequests.roots` (a `roots/list` request); the retry carries `inputResponses.roots` |
| server sends `sampling/createMessage` | `trigger-sampling-request` answers `input_required` with `inputRequests.sampling`; the retry carries `inputResponses.sampling` |
| server sends `elicitation/create` (form) | `trigger-elicitation-request` answers `input_required` with `inputRequests.form`; the retry answers it |
| a second `elicitation/create` after the first answer | `trigger-multi-step-elicitation`: three requests, each retry carrying the new `inputResponses` and the server's opaque `requestState` |
| URL elicitation, declined | unchanged in kind (phase 3's `decline`); not in the recorded tour |
| `ping`, `logging/setLevel`, `resources/subscribe`, `notifications/roots/list_changed` | removed (`-32601`); a log level rides in `_meta`, subscriptions are `subscriptions/listen` |
| the server's 2025 re-lists and updates, unsolicited | delivered only on a listen stream that asked for them |

## source-tour

The opening message to the factory that registers the modern tool set, one hop at a time.

1. **The server reads stdin.** The launcher runs `main` on the process's stdio
   (`servers:src/everything/transports/stdio.ts:93` "await main(stdin, stdout)"), which gives
   them to the SDK's stdio transport (`servers:src/everything/transports/stdio.ts:60`
   "new StdioServerTransport(stdin, stdout)").
2. **`serveStdio` chooses the era from the first message.** The factory is handed to the SDK's
   `serveStdio` (`servers:src/everything/transports/stdio.ts:49` "serveStdio("). The SDK server
   package (`@modelcontextprotocol/server`, `dist/stdio.mjs`, `classifyOpeningMessage`) reads the
   first line: an `initialize` without an envelope pins the 2025 era; any request whose
   `params._meta` carries `io.modelcontextprotocol/protocolVersion` pins 2026-07-28. That code is
   in the SDK and is not cited here (measured, requirements recon).
3. **The factory is called with the era.** `serveStdio` calls the factory
   (`servers:src/everything/transports/stdio.ts:50` "({ era }) => {") and the factory builds the
   instance for that era (`servers:src/everything/transports/stdio.ts:51` "createServer({ era })").
4. **`createServer` registers the era's capabilities.** The one factory serves both eras
   (`servers:src/everything/server/index.ts:4` "One factory backs every transport and both eras"),
   builds the `McpServer` (`servers:src/everything/server/index.ts:126` "new McpServer("), declares
   the tasks extension on the modern era only
   (`servers:src/everything/server/index.ts:151` "extensions: { [TASKS_EXTENSION]: {} }") and
   registers the tools (`servers:src/everything/server/index.ts:180` "registerTools(server, context)").
5. **The modern tool set.** `registerTools` registers the tools every client gets on either era
   (`servers:src/everything/tools/index.ts:42` "Register the tools every client gets"), including the list-change trigger
   (`servers:src/everything/tools/index.ts:57` "registerTriggerListChangedTool(server, context)")
   and the research-query task tool
   (`servers:src/everything/tools/index.ts:124` "registerSimulateResearchQueryTool(server)").
   A tool that needs the client (roots, sampling, elicitation) answers `input_required` on this
   era (`servers:src/everything/tools/get-roots-list.ts:4` "returns `input_required` carrying").

## departures

The server's measured behaviour where it differs from the 2026-07-28 spec. They are recorded and
explained, not worked around.

- **Progress after cancellation.** The tour cancels a long-running call after its first progress
  notification and the server still sends the second one (the tour waits for it and the trace
  shows it as `s2c.notifications/progress.3`). The spec says a server stops work and sends nothing
  further for a cancelled request (`spec:docs/specification/2026-07-28/basic/transports/stdio.mdx:82`
  "MUST NOT** send any further messages for it"). The tool ignores the cancellation, as in the 2025
  era; no response follows, which is the part the server gets right.
- **A later request claiming another version, on a pinned connection, is served.** After the
  opening message pins 2026-07-28, a request whose envelope claims `2025-11-25` is answered
  instead of refused. The spec makes a request's version a per-request fact the server checks
  (`spec:docs/specification/2026-07-28/basic/versioning.mdx:59` "-32022"). Measured in the recon;
  the tour does not send such a request, so no trace shows it (experiment: `manual`).
- **No `subscriptions/listen` response at shutdown.** When stdin closes (or the client cancels
  the listen request) no response to the listen request is sent. The spec says a server that ends a
  subscription on its own initiative SHOULD send a successful response
  (`spec:docs/specification/2026-07-28/basic/patterns/subscriptions.mdx:122` "SHOULD** send a").
  The tour closes its stream itself with `notifications/cancelled`, so its trace shows none.

## tour

#### `c2s.server/discover.0`

The first message, and the first difference from 2025: there is no `initialize`. The client asks
`server/discover`, the call that tells it what the server is
(`spec:docs/specification/2026-07-28/server/discover.mdx:7` "lets a client query a server's supported protocol versions"),
because a client that speaks both eras SHOULD probe like this on stdio
(`spec:docs/specification/2026-07-28/server/discover.mdx:78` "legacy (`initialize` handshake) servers **SHOULD**").
Calling it is optional in the spec (`spec:docs/specification/2026-07-28/server/discover.mdx:64`
"is optional for clients"); the raw client makes it mandatory and sends nothing else until the
reply arrives, which is stricter. Its `params` hold only `_meta`, the envelope every request now
carries (`spec:docs/specification/2026-07-28/basic/index.mdx:368` "fields marked as required **MUST** be included on every request"):
the protocol version `2026-07-28`, the client's name and version, and `clientCapabilities`, here
the roots, sampling and form-elicitation capabilities the tour declares. Its id is `0`.

```json
{"jsonrpc":"2.0","id":0,"method":"server/discover","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{"name":"wire-lab-raw","version":"0.2.0"},"io.modelcontextprotocol/clientCapabilities":{"roots":{"listChanged":true},"sampling":{},"elicitation":{"form":{}}}}}}
```

#### `s2c.response.0`

The `DiscoverResult`: `supportedVersions` (`["2026-07-28"]`), the server's `capabilities`
(tools, prompts, resources with subscribe and list changes, logging, completions and the tasks
extension), `instructions`, and the server's name in `_meta["io.modelcontextprotocol/serverInfo"]`
(`spec:docs/specification/2026-07-28/server/discover.mdx:98` "serverInfo"). Like every result it
carries `resultType` (`spec:docs/specification/2026-07-28/basic/index.mdx:73` "**MUST** include a `resultType` field"),
here `complete`, and, because discovery may be cached, `ttlMs` and `cacheScope`
(`spec:docs/specification/2026-07-28/server/utilities/caching.mdx:43` "`ttlMs`, is an integer value in milliseconds").
The client checks that `2026-07-28` is in `supportedVersions` before it lets any other request go;
a server that offers other versions only, or answers with `-32022`, stops the client with the
versions it offered, and any other error stops it with a hint to try `--era 2025-11-25`.

## tasks

#### `c2s.tools/call.1`

`simulate-research-query` from a client whose envelope for **this** request leaves out the tasks
extension. Elsewhere in this run the envelope declares sampling, form elicitation and
`extensions: {"io.modelcontextprotocol/tasks": {}}`; here only the first two.

#### `s2c.response.1`

`-32021`: the tool needs the tasks extension and the request did not declare it. A server
MUST NOT return a task to a client that did not declare the extension on that request
(`spec:seps/2663-tasks-extension.md:87` "MUST NOT** return `CreateTaskResult` to a client"), and says which capability it needs.
The pinned `schema.json` does not define tasks at all, so the checker reads the extension's
frames against a transcription of SEP-2663 (see *shared*).

#### `c2s.tools/call.2`

`trigger-sampling-request-async` with the extension declared: a tool that asks the client's model
for something, as a task.

#### `s2c.response.2`

Not a tool result: a task handle. Its `resultType` is `task`
(`spec:seps/2663-tasks-extension.md:128` "MUST** set `resultType` to"), it carries the task's id and status
(`spec:seps/2663-tasks-extension.md:137` "interface Task {"), and its status is already
`input_required`, with `inputRequests` holding the sampling request. The client's classifier
accepts `task` only for a request that declared the extension. The task is the only one of the
two new MRTR shapes that lives past one request.

## shared

Tasks in this run are checked against a transcription, not against the normative schema. The
pinned `schema/2026-07-28/schema.json` has no definition of any `tasks/*` message or of a task
handle; the extension exists at the pin only as the TypeScript types of SEP-2663
(`spec:seps/2663-tasks-extension.md:137` "interface Task {"). `tap/schemas/2026-07-28/sep-2663-tasks.json` is a hand transcription of those types into
the JSON Schema keywords `tap.check` implements; every definition cites its SEP line, and every
report names a frame checked against it `SEP-2663:<Name>`. It checks shapes only: the SEP's prose
rules (ISO 8601 timestamps, integer milliseconds, unique `inputRequests` keys) and whether a task
was sent to a client that declared the extension are not checked. With `--no-extensions` the same
frames are `unknown method`: that is the limit of the pinned schema, made visible. One reading
aid: for a malformed task, the schema's `anyOf` reports the status variant that came closest, so
a `completed` task without `result` can be reported against the `working` variant's `status`.

#### `tap.spawn.0`

The tap starts the server as a child process: over stdio the client launches the server
(`spec:docs/specification/2026-07-28/basic/transports/stdio.mdx:7` "the client launches the MCP server as a subprocess"), and here the raw client launches the tap, which launches
the server so that it can watch both directions. The `spawn` record lists the command and the
minimal environment `scripts/record.sh` gives the server. The launcher's entry point is
`servers:src/everything/index.ts:25` "./transports/stdio.js".

#### `stderr.0`

Not protocol. The server's boot line on stderr (`servers:src/everything/transports/stdio.ts:92`
"Starting default (STDIO) server..."), which the spec lets a server write
(`spec:docs/specification/2026-07-28/basic/transports/stdio.mdx:14` "MAY** write UTF-8 strings to `stderr`") and tells clients not to read as an error
(`spec:docs/specification/2026-07-28/basic/transports/stdio.mdx:17` "SHOULD NOT** assume `stderr` output indicates error conditions"). The raw client does not touch the child's stderr.

#### `c2s.server/discover.0`

The opening message of every run in this era: `server/discover`, with the envelope (see the
`tour` section for the full note). Its arrival, rather than an `initialize`, is what tells the
server's `serveStdio` that this connection speaks 2026-07-28
(`servers:src/everything/transports/stdio.ts:50` "({ era }) => {").

#### `s2c.response.0`

The `DiscoverResult`: `supportedVersions`, capabilities (including the tasks extension), the
server's name, and the cache fields. The client proceeds only because `2026-07-28` is in the list.

#### `tap.exit.0`

The server's exit, recorded by the tap. The client shut the server down as the stdio lifecycle
says: close its stdin, wait, and only then `SIGTERM` and `SIGKILL`
(`spec:docs/specification/2026-07-28/basic/transports/stdio.mdx:91` "Closing the input stream to the child process"). The server exits on end of input
(`spec:docs/specification/2026-07-28/basic/transports/stdio.mdx:102` "exit promptly when their standard input is closed"), here with code 0. A run in which the client sent `initialize` to this
2026-pinned connection would see exit code 1 instead (experiment in lesson 06).

## era-diff

What `tap.diff` reports between a fresh 2025 `tour` and a fresh `tour-2026` trace, entry by entry.
Keys are paired by method and occurrence, not by position: **the n-th `tools/call` of one era is
paired with the n-th of the other even when they are different calls** (the 2025 tour's third and
fourth `tools/call` are the long-running ones; the 2026 tour's are the log-level steps). Messages
that are equal once ids are normalised (the four progress notifications and the first
`notifications/cancelled`) are not entries.
