# Lesson 06: the same client, a new era

<!-- exercises: server/discover, tools/list, tools/call, resources/list, resources/templates/list, resources/read, prompts/list, prompts/get, completion/complete, subscriptions/listen, notifications/cancelled, notifications/progress, notifications/message, notifications/subscriptions/acknowledged, notifications/tools/list_changed, notifications/prompts/list_changed, notifications/resources/list_changed, notifications/resources/updated, roots/list, sampling/createMessage, elicitation/create -->

## Goal

Speak both eras of the protocol from one client and say what each 2025 message became. The raw
client of lessons 02 and 03 speaks 2025-11-25. This lesson runs it with `--era 2026-07-28`, the
newer revision, which changes five things:

1. **No handshake.** `initialize` and `notifications/initialized` are gone. The client may first
   send `server/discover`, a request whose reply lists the versions the server speaks, its
   capabilities and its name.
2. **An envelope on every request, and no session.** `_meta` is the member of `params` that the
   protocol keeps for metadata about a message rather than its content. In 2026 every request
   carries there the protocol version, the client's name and the client's capabilities: the
   *envelope*. The server remembers nothing between requests, so each one must say it all again.
3. **Questions to the client travel inside results.** The server may no longer send the client a
   request (`roots/list`, `sampling/createMessage`, `elicitation/create`). It answers the client's
   own request with a result of type `input_required` that holds the question, and the client
   sends the same request again with the answer. The spec calls this *Multi Round-Trip Requests*;
   one tool call can take several rounds.
4. **A subscription stream instead of unasked notifications.** Change notifications arrive only
   after the client opens a stream with a `subscriptions/listen` request that says which changes
   it wants (this replaces `resources/subscribe`). Each notification on the stream is tagged with
   the id of that request.
5. **Tasks are an extension.** A task is a job the server runs on after it has answered: it
   replies to a `tools/call` with a *task handle* (a result with `resultType: "task"` and a task
   id) instead of the tool's result, and the client asks for the result later with `tasks/get`.
   Tasks are no longer in the core protocol but in an optional extension, specified in SEP-2663
   (a SEP, Specification Enhancement Proposal, is the document that proposes and specifies a
   change to MCP). A client that wants tasks declares the extension in its envelope.

Walkthrough 06's table [Five shifts](../walkthrough/06-era-2026.md#five-shifts-and-what-each-2025-message-became)
maps each 2025 message to what it became, and its
[departures](../walkthrough/06-era-2026.md#departures) section lists where the pinned server does
not do what the spec says. You will record both eras against the pinned server, check the new one
against the specification's JSON Schema, diff the two eras message by message, and then break
things by hand.

Setup, once: `scripts/bootstrap.sh` (see the README). Everything below runs from the repo root.
Lessons 01 to 03 come first: this one assumes you know `initialize`, how the raw client sorts a
line into a response, a request or a notification, and what a server-to-client request is.

## Read the source

The new era is one module, `client/modern.py`, so the diff of the eras is the diff of that file
against `client/session.py`:

- `envelope`: the one function that builds every request's `params._meta`. The reserved keys
  are the client's; the caller's other keys (a `progressToken`) survive.
- `ModernSession.discover`: the version check that replaces `Session.initialize`, and
  `ModernSession._require_ready`, the gate that lets nothing through before its reply.
- `classify_result`: the decision by `resultType`, which turns a result into a result, an
  `InputRequired` outcome, a task handle (only for a request that declared the extension) or an
  error.
- `ModernSession.request_with_input`: the loop that lesson 03's server-to-client requests became.
  `requestState` is copied, never parsed.
- `Registry` and `ModernSession.listen`: notifications routed by the subscription id in `_meta`
  and nothing else, the id's type included.
- On the server side, follow the opening message to the factory: the source tour in
  [the walkthrough](../walkthrough/06-era-2026.md) (`## source-tour`).

The schema side: `tap/check.py` (`load_extension`, the `input_required` and `task` rules) and the
transcription it loads, `tap/schemas/2026-07-28/sep-2663-tasks.json`, each of whose definitions
opens with the SEP line it is transcribed from.

## Experiments

Manual mode in the new era discovers first, then sends exactly the lines you type. A line that
starts with `{` is sent as it is; `:req <method> [<params>]` wraps the params in the envelope.
To type them yourself run
`python3 -m client manual --era 2026-07-28 -- node vendor/servers/src/everything/dist/index.js stdio`.
The outcomes below were **measured against the pinned server**; they are what it did, not
what the spec promises.

**1. Send a method that was removed.** `ping`, `logging/setLevel` and `resources/subscribe` are
gone from 2026-07-28. What does the server say?

<!-- run -->
```console
$ printf '%s\n' ':req ping' ':req logging/setLevel {"level":"debug"}' ':req resources/subscribe {"uri":"demo://x"}' | scripts/record.sh --client manual-2026 lesson06-removed > /dev/null 2>&1
$ run=$(ls -dt runs/*-lesson06-removed | head -1)
$ python3 -m tap.show "$run/trace.jsonl" | grep -o 'error id=[0-9]* code=-*[0-9]*'
```

<!-- expect -->
```text
error id=1 code=-32601
error id=2 code=-32601
error id=3 code=-32601
```

Measured: method not found, three times (ids 1 to 3: the discover was 0). Run `tap.check` on that
trace: the removed methods have no 2026 definition, so it reports them as `unknown method`, which
is why a recorded tour never sends them.

**2. Take the capabilities away.** Run the tour with `--caps none`. Which step fails, and with what
error?

<!-- run -->
```console
$ python3 -m client tour --era 2026-07-28 --caps none -- node vendor/servers/src/everything/dist/index.js stdio 2>&1 | grep -o 'FAILED  RpcError' | head -1 || true
```

<!-- expect -->
```text
FAILED  RpcError
```

Before you read the output, predict the step number of the failure; then read the whole output.

<details>
<summary>Answer</summary>

Step 21, the `get-roots-list` call that should succeed, fails with `-32021` and the tour stops
there (it exits 1). Step 20, the `-32021` step, passes, because the tour expects that error: it
sends no capabilities on purpose. Step 21 normally sends the tour's capabilities, but with
`--caps none` the client really declared nothing, so the server refuses again. In 2025 the tool
would not even have been listed.

</details>

**3. Check the tasks trace without the extension schema.** `--no-extensions` checks against the
pinned `schema.json` alone:

<!-- run -->
```console
$ run=$(ls -dt runs/*-lesson06-tasks | head -1)
$ python3 -m tap.check "$run/trace.jsonl" --revision 2026-07-28 --no-extensions | grep -c 'unknown method' || true
```

<!-- expect -->
```text
10
```

Measured: exactly the ten `tasks/*` frames (five requests and five responses), and nothing else
fails: the task handles still pass as ordinary `CallToolResult`s. Compare with the run in *Read the
trace*: with the transcription, those frames are checked, and say so.

**4. Change the client, predict the trace.** In `client/modern.py`, make `request_with_input` stop
sending `requestState` on its retries (delete the line `current["requestState"] = result.request_state` and the `if result.request_state is not None:` above it).
The tour then fails, and `scripts/record.sh` says "the run ended with exit code 1"; the trace is still written
and is part of the answer. Before you record
`tour-2026` again, predict what the server answers to the retry of `trigger-multi-step-elicitation`
and which line of `tap.check` output changes. Then undo the edit with
`git checkout client/modern.py`, so the client is the original again (the lesson checks run against it).

<details>
<summary>Answer</summary>

Measured: every retry is answered `input_required` with the first question again, "What is your
name?". Without `requestState` the server has no memory that the name was given: the state is the
only place it keeps the step it is at
(`servers:src/everything/tools/trigger-multi-step-elicitation.ts:112` "switch (state?.step) {").
The client gives up after five requests (`TooManyRounds`), so the tour fails at step 24 and never
closes its subscription. `tap.check` still says `ok`; only the frame count changes,
`check: ok (77 frames)` instead of `74`, because each extra request and reply is valid on its own.
A schema check proves each message is well formed, not that the conversation makes progress.

</details>

## Check yourself

Answer from your own trace, then open the answers.

1. Why is the first reply to `get-roots-list` a result and not an error, and why does the `-32021`
   step before it exist?
2. What did the client add to the second `get-roots-list` request, and which of its fields must
   not be parsed?
3. The cancelled long-running call still produced a second progress notification. What does that
   say about the server, and about what the client may rely on?
4. Why does `tap.check` say `12 of 18 frames` for the tasks trace, and which two of them are not
   `tasks/*` frames?
5. Why do `s2c.notifications/tools/list_changed` and the log messages differ in what they carry
   in `_meta`?

<details>
<summary>Answers</summary>

1. The server may not ask the client for anything: it answers its request with `input_required`
   and the question inside it. The `-32021` step shows the other case: when the request does not
   declare the capability, the server cannot ask and refuses.
2. A top-level `inputResponses` (one entry per input request) and the `requestState`, with a fresh
   id and the whole envelope. `requestState` is opaque: it is copied byte for byte.
3. The server's tool ignores the cancellation (the spec says it should stop); the client may only
   rely on its own decision to stop waiting and to drop a late reply.
4. Ten frames are `tasks/*` requests and results; the other two are the task handles, results of
   `tools/call` that carry `resultType: "task"` and are checked against `CreateTaskResult`.
5. A stream notification carries the subscription id so a client with several streams on one
   stdout can tell them apart; a log message belongs to the request in flight and carries none.

The *Predict* answers:

1. No: the server keeps nothing between requests. It reads them from that request's own
   envelope, `params._meta`, which carries the protocol version, the client's info and its
   capabilities on every request, `server/discover` included.
2. It answers `input_required` with a `roots/list` request inside, the client retries with the
   answer.
3. `io.modelcontextprotocol/logLevel` in a request's `_meta`; nothing at all.
4. By `_meta["io.modelcontextprotocol/subscriptionId"]`, which equals the id of the listen
   request.
5. `unknown method` for each `tasks/*` frame, never `valid`; it can check them against a
   transcription of SEP-2663's types instead, and says so in its report line.

</details>
