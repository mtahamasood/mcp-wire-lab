# Phase 4 — Edge lab: requirements

Lean profile (LP1–LP6 in `mission.md`; register row 2026-10-21, lean profile). Phase 1's
decisions D1–D16 stand unless amended here; they are not restated. This phase needs no raw
client: its experiments are hand-written fixtures sent by the phase 1 driver, so it is
built in parallel with phase 2 (A24).

## Learning objective

Learn the protocol's contract from its error paths: for each malformed or out-of-order
message, predict the server's reply from the spec, record it, and explain where the server
follows the spec, where it is stricter or looser, and why. Then see timeouts and
cancellation by injecting delay and loss in the tap.

## Scope

In: the edge fixtures (D1), the driver change they need (D2), the tap fault mode (D3), the
walkthrough and lesson 04 (D4). Out: any change to the server; a fault mode for stderr;
HTTP (phase 7).

### D1 — Edge experiments are fixtures, one rule each

Each experiment is a hand-written fixture `tests/fixtures/edge-<name>.ndjson` of NDJSON
messages, as in phase 1 (not trace-shaped, so G11 does not apply). Each one first completes the
2025 handshake (except where the experiment is the handshake), then breaks exactly one
rule. The set is the roadmap's L11 list: `missing-jsonrpc` (a request without
`"jsonrpc"`), `before-initialize` (a request before `initialize`; phase 1's
`exp-list-first` covers the 2025 handshake order and is reused, not copied),
`unknown-method`, `duplicate-id` (two in-flight requests with one id), `string-id` (the
same request with `"id": "1"` and `"id": 1`), `notification-with-id` (a
`notifications/…` method carrying an `id`), `batch-array` (a JSON array of two requests),
`oversized-frame` (one `tools/call` whose argument is a string of 1 MiB, generated by
the test that records it rather than committed). The experiment is named by its file
name and described in the walkthrough, not in the fixture.

*Source:* owner decision, 2026-10-20 — registered in mission.md (A4, delegated; roadmap
L11).

### D2 — The driver can wait for no reply

Some edge messages get no reply by design (a malformed request the server drops, a
notification). The driver (phase 1 D9) gains one per-fixture mechanism: a line whose
JSON object carries the member `"_drive": {"expect": "none", "wait_ms": <n>}` is sent
with that member removed, and the driver waits `n` milliseconds instead of waiting for a
matching id. A line whose member says `"expect": "reply"` keeps today's behaviour. The
driver still never builds or decides a message (D9): it removes one member it owns and
forwards the rest byte-for-byte as the fixture wrote it, minus that member. A line that
is not a JSON object is sent unchanged and, if it has no `_drive`, waits on nothing.

*Source:* owner decision, 2026-10-20 — registered in mission.md (A4, delegated; roadmap
L11); phase 1 D9 is amended by register row 2026-10-21, lean profile.

### D3 — The tap fault mode

`python3 -m tap` gains two opt-in options, off by default:
`--delay <dir>:<ms>` holds every frame in direction `c2s` or `s2c` for `ms` milliseconds
before forwarding it, and `--drop <dir>:<method>` drops the first frame in that direction
whose `method` equals `<method>` instead of forwarding it. Each fault is recorded on the
trace's timeline as `{"dir":"tap","event":"fault","kind":"delay"|"drop", …}` with the
affected frame's `seq`; a dropped frame is still recorded as a frame (it was on the wire
into the tap) and the fault record says it went no further. Without these options the
tap's bytes, trace and lifecycle are exactly phase 1's (D1–D4). Delay preserves order
within a direction.

*Source:* owner decision, 2026-10-20 — registered in mission.md (A4, delegated; roadmap
L11).

### D4 — Walkthrough and lesson 04

`docs/walkthrough/04-edge-lab.md` explains each edge fixture's fresh trace, frame by frame,
in the phase 1 walkthrough note format (anchors per phase 1 D11), each server reply
compared with the spec's rule (verified citations, G8) and, where the server's code
decides it, the source line. Each experiment ends with a one-line verdict: *follows the
spec*, *stricter*, *looser*, or *spec silent*. `docs/lessons/04-edge-lab.md` has the L1
sections, records two edge fixtures and one fault-mode run in runnable blocks (G9), and
`README.md` lists it. The fault-mode run is explained in the lesson, not the walkthrough.

*Source:* owner decision, 2026-10-20 — registered in mission.md (A4, delegated; roadmap
L1, L5, L11); per-phase walkthrough P3.
